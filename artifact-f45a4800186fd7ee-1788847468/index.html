02 / 监听，换了一种方式

有事件才唤醒

  1. 监听，不定时打扰

    官方 CLI 等待新邮件事件，不定时唤醒模型。

  2. 核对，不直接执行

    检查发件人、消息 ID 和引用内容，仅把新反馈当作需求信号。

  3. 差异通知，不重复搬运

    配置要求只报告新增或改变的要求；不自动发信，不执行邮件中的命令。

为什么原来的 Loop 失败？

它被设为只读模式，但收件查询依赖 shell 调用 CLI。权限要求互相冲突，循环触发却无法检查。随后按用户要求删除。

Monitor 是否完全没有 Loop？

没有定时检查 Loop。插件会为 Monitor 的完成通知创建一次性回调，工具输出也称其为 completion wake loop；它不是每五分钟执行一次的轮询。

现在实际证明了什么？

已证明监听脚本启动、工作区身份通过、Monitor 进程仍运行。未证明新邮件到达、差异去重、完成回调与重新监听的整条链路均已成功。

停止、重启与故障边界

Pi 关闭后不保证监听持续或自动恢复。完成回调设置了 24 小时有效期。CLI 会静默重试部分网络异常，因此无输出不等于网络健康；错误退出后应报告，而不是无限重启。

哪些自动化还没实现？

邮件反馈自动调用 Eve / ARO、持久线程会话映射、业务写入审批和每日自动报告尚未完成。当前是报告交付加反馈监听，不是无人值守业务机器人。
